# Подключение защиты к обвязке (harness)

CLI, который нужно не забыть вызвать, — это всё ещё вопрос удачи. Статья
утверждает, что проверка должна быть **структурной** — поэтому здесь её
структурная версия: обвязка запускает проверку сама, ещё до того, как команду
увидит оболочка.

`pre_tool_use_guard.py` и `antigravity_guard.py` — это хуки `PreToolUse`, которые
перехватывают команды, прогоняют конечный автомат v3 с правильной грамматикой
оболочки и блокируют выполнение, когда команда могла бы повиснуть.

## Google Antigravity

В корне рабочей области `.agents/hooks.json` (или глобально в
`~/.gemini/config/hooks.json`):

```json
{
  "quote-parity-guard": {
    "PreToolUse": [
      {
        "matcher": "run_command",
        "hooks": [
          {
            "type": "command",
            "command": "python /path/to/llm-token-architect/hooks/antigravity_guard.py",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

### Контракт Antigravity

Antigravity использует JSON и на stdin, и на stdout:

- **Вход (stdin):** `{"toolCall": {"name": "run_command", "args": {"CommandLine": "..."}}}`
- **Выход (stdout):** `{"decision": "allow"}` — пропустить, или
  `{"decision": "deny", "reason": "..."}` — жёстко заблокировать выполнение.

`antigravity_guard.py` переводит вызовы инструментов, вызывает `parity_check.py`
с соответствующей грамматикой оболочки (PowerShell в Windows, POSIX в Unix) и
возвращает структурированное решение.

Проверка: `python tests/test_antigravity_hook.py` (12 проверок). Файл на 101 байт,
который только вызывает `sys.exit(0)`, — это заглушка, а не хук; он не выдаёт
JSON и не проходит первую проверку.

### Проверено на 2.29.0.0, 7 ноября 2026

Всё в этом подразделе измерено на **Antigravity 2.29.0.0** — сборке, чьи архивы
фиксируют `app_version = 2.29.0.0` и которую в примечаниях к выпуску называют
2.29 / 44.5.1. Это не утверждение про другие сборки: API хуков молодой, и
обновление может изменить что угодно. Если хук перестал срабатывать после
обновления, снова прогоните проверки в конце этого подраздела, прежде чем
предполагать, что защита сломалась.

**Область действия.** Существуют два уровня, и проектный имеет приоритет, где
применим:

| Уровень | Файл | Применяется к |
|---|---|---|
| project | `<workspace>/.agents/hooks.json` | этой рабочей области |
| user | `~/.gemini/config/hooks.json` | каждой рабочей области на машине |

Измерено: при наличии только пользовательского файла хук срабатывает в не
относящихся к делу рабочих областях — сессия в `C:\2` выдала в лог и строки
`ok`, и `BLOCKED`, хотя файл защиты лежал под `C:\1`. Удаление проектного файла —
поэтому смена области действия, а не уборка.

**Отключение.** Используйте флаг, а не сломанный путь:

```json
{"type": "command", "command": "...", "timeout": 5, "enabled": false}
```

Направить `command` на отсутствующий файл тоже останавливает защиту, но делает
это через сбой хука: хост сообщает об ошибке при каждом вызове инструмента и
блокирует команду. Это fail-closed и шумно — измерено — но это неисправность, а
не настройка, и она не оставляет способа отличить «отключено» от «сломано».

**Конфиг читается при каждом вызове, а не при старте.** Смена пути вступила в
силу на следующем `run_command` без перезапуска. Поэтому не полагайтесь на
перезапуск для применения изменения — и не предполагайте, что запущенная сессия
всё ещё использует конфиг, с которым стартовала.

**Другие источники хуков.** Плагин может поставлять свой собственный
`hooks.json`, рядом со `skills/`, `agents/`, `rules/` и `mcp_config.json`. Когда
команда заблокирована, а в пользовательской конфигурации о ней ни слова,
проверьте список плагинов, прежде чем подозревать защиту. На установке, где
проводились измерения, присутствовал один плагин и хуков он не поставлял, так что
источник был ровно один — свойство той установки, а не дизайна.

**`PostToolUse` здесь не используется.** Защита — только хук `PreToolUse`. В
`PostToolUse` следовало бы разместить «прогон тестов после изменения файла
хука» — шаг, который проще всего пропустить, когда правка кажется тривиальной, —
но ничего туда не подключено, и эта README не должна подразумевать обратного.

**Три проверки, две минуты.** (1) `touch debug.on`, запустите команду, прочитайте
лог — это отвечает на «срабатывает ли он вообще». (2) Повторите в другой рабочей
области — это отвечает на «проектная или машинная область». (3) Направьте
`command` на отсутствующий файл и запустите команду — она должна быть
**заблокирована**; если она выполняется, хост работает в режиме fail-open, и
защита — декорация.

## WorkBuddy AI

Конфиг: `~/.workbuddy-ai/settings.json` — ключ `hooks` на верхнем уровне:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell|Shell|Terminal|run_command|execute_command",
        "hooks": [
          {
            "type": "command",
            "command": "\"C:\\Users\\<you>\\AppData\\Local\\Programs\\Python\\Python313\\python.exe\" \"C:\\Users\\<you>\\.workbuddy-ai\\hooks\\quote_guard.py\"",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Скопируйте `pre_tool_use_guard.py` → `~/.workbuddy-ai/hooks/quote_guard.py` и
`parity_check.py` → `~/.workbuddy-ai/hooks/parity_check.py` (хук импортирует
модуль сначала из собственной директории). Хуки читаются при старте сессии —
перезапустите приложение, чтобы изменения вступили в силу.

Используйте абсолютный путь к Python, который переживёт обновление.
Управляемый интерпретатор под `binaries/python/versions/<x.y.z>/` меняется вместе
с версиями; системный Python — нет. Замените `<you>` и `Python313` в примере на
ваш реальный путь пользователя и версию Python.

## Claude Code

Та же схема, `~/.claude/settings.json` или `.claude/settings.json` в корне
проекта:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python /path/to/llm-token-architect/hooks/pre_tool_use_guard.py"
          }
        ]
      }
    ]
  }
}
```

Если ваша обвязка предоставляет инструмент `PowerShell`, добавьте его в
`matcher` — иначе хук никогда не увидит эти команды.

## Контракт (Claude Code и стандартные обвязки)

| Канал | Значение |
|---|---|
| stdin | `{"tool_name": "Bash", "tool_input": {"command": "..."}}` |
| exit 0 | разрешить |
| exit 2 | блокировать, stderr возвращается модели как причина |

Код выхода 2 — не декорация: большинство обвязок трактуют **сбой** хука
(exit 1) как «хук упал, продолжай». Защита, которая отказывает в открытом
режиме (fail-open), — это декорация.

Хук также выходит с кодом 2, когда не может запуститься вовсе (отсутствует
`parity_check.py`, неразбираемая нагрузка). Это fail-closed, а не вердикт по
команде: прочитайте stderr, почините хук и не переписывайте команду, которую
никто не судил.

## Грамматика следует за инструментом, а не за ОС

Это та часть, которая решает, переживёт ли хук неделю.

В WorkBuddy на Windows инструмент `Bash` запускает Git Bash (грамматика POSIX),
тогда как `PowerShell` — **отдельный инструмент**. Угадывать грамматику по
операционной системе — значит применять правила POSIX к PowerShell и блокировать
`dir "C:\"`, что там абсолютно корректно.

Поэтому хук сопоставляет инструмент → грамматику:

| Инструмент | Грамматика |
|---|---|
| `Bash`, `Shell`, `Terminal`, `sh`, `bash`, `run_command`, `execute_command` | `posix` |
| `PowerShell`, `powershell`, `pwsh` | `powershell` |
| `cmd`, `CMD` | `cmd` |
| любой другой, несущий строку `command` | **двойная проверка**, см. ниже |

Переопределите всё через `QUOTE_GUARD_SHELL=posix|powershell|cmd`. Используйте
переопределение, только если вся обвязка действительно работает в одной
грамматике. Выставить его, чтобы пропустила конкретная команда, — это как раз тот
обход, ради предотвращения которого и существует этот репозиторий.

Объявите грамматику пользовательского инструмента так:

```
QUOTE_GUARD_MAP="MyTool=posix,OtherTool=powershell"
```

## Неизвестные инструменты: двойная проверка, затем вопрос

Имя инструмента, которого нет в таблице, ничего не говорит о его грамматике.
Угадывать по ОС — это ровно та ошибка, которую делал v2, поэтому для
неизвестного инструмента команда прогоняется через **обе** грамматики, POSIX и
PowerShell:

| POSIX | PowerShell | Результат |
|---|---|---|
| safe | safe | разрешить |
| unsafe | unsafe | блокировать — строка зависает в любой оболочке |
| safe | unsafe либо наоборот | **блокировать и попросить объявить грамматику** |

Третья строка не разрешается осмотром, и это не баг в проверяльщике.
`echo "a`"b"` (зависание в POSIX, сбалансированная строка в PowerShell) и
`dir "C:\"` (рабочая команда в PowerShell, зависание в POSIX) дают **одну и ту
же** пару вердиктов. Одна строка — атака, другая — команда, которую v3
существует, чтобы не блокировать. Никакое правило над самой строкой не отличит
их — только знание о том, какая оболочка её выполнит.

Поэтому защита не угадывает: она блокирует неоднозначный случай один раз и печатает
точную строку, которая его разрешает, `QUOTE_GUARD_MAP=<tool>=<grammar>`. После
этого команда судится по своей реальной грамматике и проходит, если она там
корректна.

Цена названа намеренно и того стоит: совсем новый инструмент, запускающий
корректную в одной оболочке команду, блокируется, пока не объявлен. Это одна
строка конфигурации на инструмент, один раз, в обмен на то, что неправильная
грамматика никогда не применяется молча. Когда двойная проверка блокирует
корректную команду, запишите её в
[guard_false_positives.md](../guard_false_positives.md) — не отключайте защиту.

`QUOTE_GUARD_TOOLS=name1,name2` всё ещё существует для обратной совместимости. Он
помечает имя как известное, но **не** объявляет грамматику, поэтому хук
откатывается к ОС-умолчанию и так и пишет в stderr — он никогда не угадывает
молча.

## Один предохранитель, один смоделированный случай

**Неизвестные инструменты всё равно проверяются.** Если имени инструмента нет в
таблице, но нагрузка несёт строку `command`, хук проверяет её всё равно. Немой
no-op из-за неожиданного имени инструмента *выглядел бы* как защита, не
предоставляя её.

**Хередоки маскируются, а не пропускаются.** Тело хередока читается дословно до
его разделителя, поэтому кавычки внутри него не могут повесить оболочку — но на
лексере построчного уровня они выглядят несбалансированными. Лексер обнуляет тело
(сохраняя длину и переводы строк) и проверяет то, что реально выполняется.
Незавершённый хередок сам по себе — это зависание и блокируется как
`state=HEREDOC`. Это заменило старое поведение «пропустить всю команду
целиком», которое было fail-open: несбалансированная кавычка *после* терминатора
проходила незамеченной.

## А он вообще срабатывает?

```bash
touch ~/.workbuddy-ai/hooks/debug.on
```

добавляет по одной строке на решение в `quote_guard.log` рядом с хуком: `ok`,
`blocked`, `note: unknown tool ...`, `skip: empty payload` / `skip: ... no
command field`. Строка `skip: heredoc` означает, что установленный хук старее
v3.1.2 — обновите его. Перезапустите, запустите несколько команд, прочитайте лог.
«Хук установлен» и «хук работает» — разные утверждения, и проверить можно только
одно из них.

Почему файл-флаг, а не `export QUOTE_GUARD_DEBUG=1`: **установка переменной
окружения в терминале не доходит до хука.** Хук порождается приложением, поэтому
наследует окружение приложения, а не вашей оболочки. Файл-флаг читается при
каждом вызове, поэтому не требует перезапуска и не требует инфраструктуры
окружения. Переменная окружения всё ещё работает, если задать её на уровне ОС и
перезапустить приложение.

## Другие обвязки

Адаптируйте в двух местах: `TOOL_SHELL` (имена → грамматика) и
`extract_command()` (где строка команды живёт в вашей нагрузке). Третье место
важно, если обвязка может запускать `cmd`: добавьте его в `UNKNOWN_SHELLS`,
потому что двойная проверка неизвестного инструмента покрывает только POSIX и
PowerShell. Сама защита (`parity_check.analyze`) не зависит от обвязки.

## Не любите возиться с хуками?

Оберните CLI напрямую:

```bash
python parity_check.py -c "$CMD" --shell posix || exit 1
eval "$CMD"
```

Та же проверка, только больше что забыть — и только для буквальной строки. Этот
сниппет — bash/Git Bash: он жёстко прописывает `--shell posix`, а `eval "$CMD"` —
это POSIX. Для PowerShell используйте `--shell powershell` и
`Invoke-Expression $CMD`; эквивалент `|| exit 1` —
`if ($LASTEXITCODE -ne 0) { exit 1 }`. Иначе вы проверяете одну грамматику, а
выполняете другой. Он не видит сквозь `eval`, `Invoke-Expression`,
`-EncodedCommand` или вложенную оболочку.

`|| exit 1` останавливается на любом ненулевом: UNSAFE, сбой защиты или ошибка
использования. Он их не различает. Это fail-closed, а не диагностика: для
добровольной предполётной проверки не выполнять безопаснее, чем выполнить то, что
никто не судил, — но вы не узнаете, какой случай наступил.
