# zenodo/ — снимок опубликованного

Три записи проекта живут на Zenodo, а их исходники — здесь. Между этими двумя
местами легко расходится: на Zenodo может стоять заголовок другой работы, лежать
PDF предыдущей сборки или описание без правки, которую уже внесли в репозиторий.
За один день такое случилось трижды, и каждый раз расхождение находилось глазами.

Этот каталог делает расхождение видимым.

| Запись | Работа | DOI |
|---|---|---|
| `23679671` | Трилогия | `10.5281/zenodo.23679671` |
| `23813780` | Препринт | `10.5281/zenodo.23813780` |
| `23817684` | Протокол аудита | `10.5281/zenodo.23817684` |

## Как пользоваться

```bash
python zenodo/snapshot.py      # обновить records.json по текущему Zenodo
python zenodo/check.py         # сверить снимок с опубликованным
```

`check.py` печатает, когда снят снимок, и возвращает:

| Код | Что значит |
|---|---|
| 0 | снимок совпадает с опубликованным |
| 1 | расхождение — печатает поле, значение в снимке и значение на Zenodo |
| 2 | сравнивать нечего: нет снимка, нет `snapshot.py` рядом или не отвечает API |
| 3 | сломался сам чекер — исключение, трейс в логе |

Коды раздельные намеренно. «Разошлось», «не с чем сравнивать» и «проверка
упала» требуют трёх разных действий: переснять, перезапустить, починить.
Один общий код возврата склеил бы их в «что-то не так» и заставил бы читать
лог, чтобы понять, что именно.

## Что сравнивается

Поля, которые имеет смысл сверять, а не всё подряд:

- `doi`, `conceptdoi` — номера;
- `title`, `version`, `publication_date`, `resource_type`, `language`, `license`;
- `creators` — имя, ORCID, аффилиация;
- `keywords`;
- `description` — целиком, чтобы diff показывал, чем именно изменился текст;
- `related_identifiers` — связи с другими записями;
- `files` — имя, размер и контрольная сумма каждого файла.

Размер и контрольная сумма файлов здесь не формальность: именно так ловится
«в записи лежит PDF предыдущей сборки», на котором мы уже потеряли время.

## Когда снимок обновлять

После каждой правки на Zenodo — осознанно, отдельным коммитом. Тогда в истории
репозитория видно, что изменилось на стороне публикации и когда. `snapshot.py`
не запускается автоматически: снимок должен отставать от реальности только
тогда, когда вы этого ещё не заметили, а не по расписанию.

Дата снятия не хранится внутри `records.json` намеренно: иначе каждый запуск
переписывал бы файл ради одной строки, и «изменилось ли что-нибудь» перестало бы
читаться по diff. `check.py` берёт дату из `git log` по самому файлу и печатает
её в шапке.

## Проверка по расписанию

Записи правятся в браузере — пуша при этом нет, поэтому обычный CI на `push`
такое не увидит. Отдельный workflow
[`zenodo-drift.yml`](../.github/workflows/zenodo-drift.yml) запускает `check.py`
по понедельникам и вручную через `workflow_dispatch`.

Красный прогон там означает не поломку кода, а «снимок отстал»: надо посмотреть,
что изменилось на Zenodo, решить, правильно ли это, и переснять отдельным
коммитом. Автоправки нет — иначе снимок перестал бы быть свидетельством и стал
бы зеркалом.
